# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A static, browser-only project about the Hamilton Model 21 marine chronometer (three.js r128 and the fonts vendored in `vendor/`; no npm, no bundler, no test suite):

- `marine-chronometer-source/chronometer-working-model/`: the interactive 3D working model, with a second tab, **Essay**: a long-form interactive essay (Ciechanowski-style) on how the chronometer keeps time at sea, whose figures are drawn from the model's own code. The model's README documents files, coordinates, timing and sources in detail; read it before changing geometry or timing.
- `marine-chronometer-source/shared/`: `escapement.js` (`makeEsc`, the escapement's solver, also run by Node in `tools/escapement.js`) and `escplan.js` (`drawEscPlan`, its plan drawing, for the walkthrough's inset, the adjuster's bench and the essay), and `almanac.js` (`ALM`, a nautical almanac and the navigator's arithmetic for the essay's sky sections, also run by Node in `tools/almanac.js`; the model README's "The almanac").
- Root `chronometer-working-model.html` is the published single-file copy of the build, fully self-contained (three.js and fonts inlined). The model's own `build.py` writes `dist/chronometer-working-model.html` (committed); the root build runs it. `python build.py` at the root regenerates it, the root copy and `site/` (the upload folder, committed); commit the regenerated root copy and `site/` with source changes. The root `README.md` is the user guide: setup, build, checks and publishing. The essay was once a page of its own (`marine-chronometer.html`); `worker.js` redirects its old address to `/#essay`.
- `vendor/`: three.js r128 (verified against cdnjs's SRI hash) and Latin-subset woff2 fonts with their licences. The page references them as `../../vendor/...`; `inline.py` inlines them at build time (and any local `<img>` file), and the root build fails if the page still loads a script, stylesheet, font or image from the network.
- `site-assets/`: `social.png` (the link preview, rendered by `tools/social.py`), `social-movement.png` (the mechanism titled for the essay, for posting; the same tool) and `_headers`, copied into `site/`; the build also copies the manual's scan from `References/` into `site/` as `navships-250-624-1948.pdf`, which the page links to beside itself; and the checks' two reports (`verification/build-verification/`, `verification/real-chronometers/`, as their `build_report.py` last wrote them) into `site/verification/` at the same paths, their `../../tools/` links pointed at GitHub, linked from About and the essay (rebuild a report before the build when what it reports changed).
- `References/` holds the source material: the 1948 NAVSHIPS 250-624 overhaul manual PDF, reference photographs and drawings. Its README lists each file, what the model took from it and its original filename. `References/VIDEOS.md` catalogues videos of real Model 21s (teardowns and a 4K restoration): what each shows minute by minute, every measurement taken on them (the train's tooth counts came from one), the methods (`tools/video.py`) and which open gaps they could close. The videos and their frames stay outside the repository.
- **No physical chronometer:** the user has no real chronometer and never will: neither an original Hamilton Model 21 nor one built from the model. Never ask them for measurements, recordings, photographs of their own, test equipment or bench results, and don't plan work that waits on them. Everything is settled from the sources (the manual, other people's photographs and videos, published literature) and the model's own analysis; what only a made chronometer could settle stays an estimate, and says so. The build-oriented tools (bench.js, benchcheck.py, rating.py, the build book, the jigs) are guidance for any maker, proved by their own demos, not a queue of the user's tasks.
- **Source of truth:** the manual, photographs of real Model 21s and videos of real Model 21s decide what the model looks like and does. Where the model disagrees with them, the model is wrong; estimates, clearance fits and earlier choices in the code give way. Say how sure each reading from a photograph or video is, and keep what is inferred or estimated in the model README's "Estimated, not from the manual" section.
- **Build from measured lines:** every outline, size and place you draw or change is measured first, on a photograph (`References/`), a video frame (`References/VIDEOS.md`, `tools/video.py frame`) or the manual's figure or text: traced on the image and put in millimetres through the tools (`video.py anchor`/`fit`/`unproj`, `rimfit.py`, `framecam.py`, `fcal.py`, `holes.py`), or read off a dimension the manual gives. Trace lines and profiles: every edge and every side profile (silhouettes, undersides, steps, wall profiles) is traced on the image as points and built from them, never a stock form (a quarter-circle cove, a straight bar, a plain cylinder) in place of a line a frame shows; before deciding a profile can't be read, sheet the video round the moment for a frame that shows it side-on. Never draw a shape by eye, from memory, from a generic chronometer or to suit clearance alone. The code comment beside it names the source (video ID and mm:ss, photograph, figure or Op.) and the measured numbers; where no source shows a line, say so, keep it an estimate in the README's "Estimated" section, and fit it as little as the measured lines around it allow.
- `RESOLVED.md` lists bugs already found and fixed (from the commit history), grouped by area, each with what to keep true. Read the relevant section before changing a part, control or build step, and don't reintroduce anything listed. When a change fixes a bug, add an entry in the same commit, under its heading, with the hash (entries for uncommitted fixes go under "Fixed, not yet committed"). `OPEN-QUESTIONS.md` lists the readings no source has settled (what is known, what conflicts, what was searched, what would settle each); `REQUESTS.md` is the post to send owners and the NAWCC for them; `IDEAS.md` holds ideas, `Review-results.md` open review findings and `PERFORMANCE.md` the frame-time measurements, what was done and what's next; neither belongs in `RESOLVED.md`.

## Build / run

From the repository root:

    python build.py                          # the model (with its Essay tab), the root copy, site/
    python build.py --site-url https://...   # also adds canonical + og:image tags to site/index.html (or set SITE_URL)
    python build.py --site-url https://... --keep-html   # for hosts that don't redirect /page.html to /page
    python build.py --release patch -m "what changed" [-m ...] --site-url https://...   # a release: the next version in CHANGELOG.md, then the build

The live site is https://www.marinechronometermodel.com, a Cloudflare Worker serving `site/` (`wrangler.jsonc`); `worker.js` redirects the bare domain, the old workers.dev address and plain http to it, and the essay's old address (`/marine-chronometer`) to `/#essay`. Pushing doesn't deploy it: release (below), commit, then `python deploy.py`.

Versions: the site's version (`M.mm.pp`, shown with the list of changes in the panel's last section, Version … · what's new, and in About's byline) is the top entry of the root `CHANGELOG.md`, which `changelog.py` reads, checks and renders into the page at build time. A plain build never changes it, so `ci.py`'s rebuild matches. Every deploy is a release: build with `--release patch` (fixes, small changes), `minor` (new features or parts, a merged branch) or `major`, one `-m` per line of what changed, written for visitors, then commit `CHANGELOG.md` with the builds and deploy with `python deploy.py`. It is enforced: `deploy.py --check`, which `wrangler.jsonc` runs before every `wrangler deploy`, rebuilds with the live address and refuses uncommitted or stale builds, a version not above the live page's (unless the page is byte for byte the same), and a version tag already on another commit; `deploy.py` then tags the commit `vM.mm.pp` (push it with `--follow-tags`). Suggest the kind and the lines; the user decides.

Merging a branch into `main`: only after `python ci.py` passes on it (below, Verification tools); always `git merge --no-ff`, so every branch lands as its own merge commit (never a fast-forward or a squash). Resolve conflicts in the built copies and `site/` by rebuilding, not by hand.

Every local branch lives on GitHub too, merged or not: push a new branch with `git push -u origin BRANCH` as soon as it has its first commit, and push again after every commit on it (and `main` after every merge, with `--follow-tags`). Never leave a local branch without its `origin` copy or behind it; `git for-each-ref --format='%(refname:short) %(upstream:short) %(upstream:track)' refs/heads` should list every branch with an upstream and no `[ahead N]`.

Open `marine-chronometer-source/chronometer-working-model/index.html` directly in a browser for development. URL flags:
- `?snap`: disables camera/state easing so views settle immediately (for screenshots), and draws every frame (without it the loop skips frames in which nothing shown changed; see the README).
- `?qa`: exposes `window.__mv` (the movement group), `__M` (the materials) and `__BX` (the box: its root, ring and bowl; massprops.py), `__proj` / `__unproj` (movement frame ↔ screen pixels for a given camera), `__cam(yaw,pitch,dist,fov)` / `__look(yaw,pitch,dist,x,y,z)` (set the camera) and `__camInfo()` (print it) for the verification tools and `social.py`, plus `__parts` (the parts registry), `__r` (the renderer), `__renders()` (frames drawn) `__H()` (stopping and starting: the balance's amplitude, whether the train is held, the arm and screw; the rate's shares and the drive) and `__test()` (the 30-day performance test's figures) and `__lp()` (winding's load-path phase and whether the sustaining spring's close-up shows) and `__cu()` (the close-up's zoom, pan, enlarged, kept open, explanation and slow motion), and `__glb(clips)` (the export to Blender, saved as a download; `gltf_check.py`).

Essay: its text and figure markup are the `<article id="essay">` in `index.html`, its styles `css/essay.css`, its figures `js/essay.js`; open `index.html#essay` (or `#essay=detent`, a section) to work on it. Facts in it come from the manual (`References/`) and the model's README, never invented; numbers the model computes (escapement figures, tooth counts, fusee radii) go in `data-live` spans that `fillLive()` sets from the model's code. The sky and workshop sections (navigation without radio; making the chronometer) may also use published literature, named in the text and the README's Sources (Meeus, Bowditch, the Nautical and Astronomical Almanacs; decision D1 in `PLAN-self-contained.md`), never outranking the manual, photographs or videos; their stated accuracy is in `data-bound` spans that `tools/almanac.js` checks.

## Working-model architecture

- The scripts are classic (non-module) scripts sharing globals, loaded in order `report.js` → `core.js` → `mainspring.js` → `../shared/escapement.js` → `../shared/escplan.js` → `../shared/almanac.js` → `../shared/hairspring.js` → `movement.js` → `box.js` → `essay.js` → `makers.js` → `maker.js` → `gltf.js` → `rigpy.js` → `blender.js` → `app.js`. `mainspring.js` declares only `MSHAPE` (the mainspring's solved states, generated by `tools/mainspring.py`: run it after changing the spring's length, thickness, core, barrel or its measured free curve; `--write` rewrites it from the last solve); `shared/escapement.js` declares only `makeEsc`, `escplan.js` only `drawEscPlan` and `escStage`, `almanac.js` only `ALM` and `hairspring.js` only `HSPR` (each keeps its own `TAU`/`D2R` inside); `makers.js` declares only `MAKERS` (generated by `tools/makers.py`: run it after changing `bom.json` or `BOM.md`) and `maker.js` only `MAKER` (the maker's sheets, drawings, STL, Measure, build book; app.js calls `MAKER.bind()`). `report.js` declares only `REPORT` (Report a bug or inaccuracy: the dialog, and the page's last errors and warnings, which is why it loads first; app.js calls `REPORT.bind()`; nothing leaves the page but through the visitor's own email). `gltf.js` declares only `GLTF` (a glTF 2.0 writer), `blender.js` only `BLENDER` (the export to Blender: its own copy of the model, every motion played through it; app.js calls `BLENDER.bind()` with `config`, which sets the copy as the page is) and `rigpy.js` only `RIG_PY` (generated by `tools/rigpy.py` from `blender/rig.py`, the Blender rig: run it after changing the rig; the model README's "The model in Blender"). `core.js` defines shared helpers (`TAU`, `clamp`, `lerp`, `smooth`, `$`, `sc`, materials, geometry builders) used by the later files; load order matters.
- `essay.js` is one IIFE that declares only `ESSAY` (`show`, `on`, `section`, `bind`): everything else in it is private, so its names can't clash with the model's. It uses the model's globals (`mats`, `gearGeo`, `arbor`, `escapeWheel`, `springGeo`, `handShape`, `dialCanvas`, `buildBox`, `ESC`, `TRAIN`, `MOD`, `L`…) lazily, when a figure is first built. app.js calls `ESSAY.bind()` once the model is built (its time, wind, fusee, the balance's moment of inertia, and `changed`, which writes the hash). While the essay shows, the model keeps time but isn't drawn (the loop's `ESSAY.on()`), and its keys are left to the essay. The essay's 3D figures share one WebGL renderer off screen, copied onto each figure's 2D canvas, so the page has two contexts in all; smoke.py checks it.
- Units are millimetres. Movement frame: dial side +y, 12 o'clock −z, 3 o'clock +x. Arbor positions live in the `L` constant at the top of `movement.js`; they come from the photo-fitting pipeline, so don't move them casually. The photographed group (balance, fusee, barrel, and everything traced on the top-view photograph with them: pillars, bridges, cock, screws, engraving, damascening) is placed against the dial and train by one similarity, `PT()` (×`PHOTO_K` 1.039, turned `PHOTO_TURN` 19.42°, shifted `PHOTO_T`; `PTi()` back), fitted so the balance, fusee and barrel land where the real movements measure them (IDEAS.md 1.12): `L` holds the results, a new constant traced on that photograph goes through `PT()` (outlines running to the rim through `PTr()`), one measured on the video in the train bridge's own frame through `PR()` (the 14° turn alone), and sizes read against the fusee wheel scale by `FK`. The main heights are the constants beside it (`TB_U`, `TB_T`, `BB_T`, `CK_T`, `EY`, `LB_T`, `BAL_Y`), measured on a side photograph; the README's layout section says which heights are measured and which are fitted for clearance.
- Single model clock `tSim`. Balance phase `p = frac(tSim/0.5)`; `ESC.state(p)` returns balance angle, detent lift, trip-spring deflection and escape-wheel tooth progress. Escape-wheel position `E` (in teeth) drives every other arbor by a fixed ratio, so hands step in half-seconds. The movement's per-frame `mv.userData.update({E, th, lift, psDef, ...})` applies this state.
- `app.js` rebuilds the environment map on `webglcontextrestored`: a restored context loses PMREM render targets, which leaves every metal flat and dark.
- Screws: `screw(parent,x,z,y,r,h,len,thread)` draws head and threaded shank; each part the shank passes through gets a clearance hole (`hC`), the part it holds a tapped hole (`hT`), from the positions in the `S` table at the top of `buildMovement`. A shank without its hole shows in `fine.py` as a new overlap.
- The balance's amplitude is state (`H.amp` in `app.js`): below `ESC.AMIN` the escapement can't unlock and the train holds, as it does at run down, with the balance locking arm locked or with the train-blocking screw's dog point against a spoke; a stopped chronometer needs Twist to start (Sec. III). It follows the balance's equation of motion averaged over a swing: A² relaxes to `ESC.ampAt(drive)²` as exp(−2t/TF), the drive being the fusee's torque, the sustaining spring's while winding, or none; the escapement's rate at that swing (`ESC.rateAt`) is `escK` in the running rate (model README, "The balance's dynamics").
- Every part is a closed solid facing out (like a CAD model): build extrusions with `extrude()` (never `THREE.ExtrudeGeometry` directly: r128 winds a hole's wall into the metal under a clockwise outline), close lathe profiles or run them to the axis at r 0, and cap anything else left open (tubes, part-turned lathes and tori) with `closeGeo()` (or, for a tube rebuilt as the model moves, `reclose(old, g)`, which rewrites the old closed geometry in place), all in `core.js`; no `DoubleSide` or `noCap` on a new part. The only surfaces are flagged `userData.decal` (engravings) or `userData.surface` (the dial's printed face, the floor's shadow). A section's cut faces are the solids' back faces, hatched by `patchSection` and drawn 0.015 mm nearer (`SEC_DEPTH`) so a part lying on the cut one doesn't show through.
- Static pieces are drawn merged (`drawMerge` in `core.js`, synced each `paint()`; Display's Performance mode, on by default, `merge=0` in the hash when off): pieces under one group sharing a material draw as one copy kept outside `__mv`, while they're all shown and wear `mat0`; a piece that moves against its group or is rebuilt leaves its batch. Merged pieces sit on layer 2, so a new raycaster over the model enables layer 2 (or all); r128's shadow pass tests layers against the main camera, so the copy casts for its pieces. The model README ("Static pieces drawn merged") has the rest.
- Parts are tagged with `userData.partName` (used for picking/descriptions and by the interference check); a part that is several things has pieces (`PIECES` in `app.js`, keys `part.k`, found from each mesh's `userData.hn` or a `pc()` tag), which the page picks, describes, colours and hides on their own while every tool still works by part; `userData.noCap` / `noShadow` / `mat0` affect cross-sections and collision filtering.
- The code is written in a dense, compact style (long one-line statements, short names). Match it when editing.
- Types without npm: `jsconfig.json` (the scripts in load order, for VS Code and `ci.py`) and `js/globals.d.ts` (three.js as `any`, `makeEsc`). `core.js`, `movement.js`, `box.js` and the two shared scripts start with `// @ts-check` and must type-check (`npx -p typescript@5.9.3 tsc -p marine-chronometer-source/chronometer-working-model/jsconfig.json`, about 10 s; `ci.py` runs it); `app.js` and `essay.js` aren't checked yet. The main surfaces carry JSDoc types: `makeEsc`'s settings (`EscSettings`, so a misspelt setting is an error), `ESC.state`'s result (`EscState`), `update()`'s argument (`MoveState`), `arbor`'s options, `part` and `screw`. Where inference fails in the dense code, a `/** @type {…} */(…)` cast says what a value is; never change the code to please the checker.

`BOM.md` (root, generated) is the parts list against the model; `Review-results.md` "BOM comparison" records what it found and what is still open.

Python scripts (numpy, scipy, Playwright + Chromium with SwiftShader WebGL) that fitted the layout to photographs and check it. Each script opens `../index.html?snap&qa` through a `PAGE` constant resolved from its own location. Outputs (`fit.json`, `p3fit.json`, `unproj.json`, `bundle.npy`, `r_*.png` screenshots) are written to the current directory, and `unproj.py` reads the `fit.json` that `fit.py` wrote there. The committed JSON files (`p3map.json`, `cock_outline.json`, `engr.json`) are traced photo data the model was built from, not tool output to regenerate.

- `fit.py` / `unproj.py`: fit the camera of the Fig. 2 photograph to the model, then unproject photo points onto the movement at known heights.
- `bundle.py`: two-camera fit / triangulation of balance, fusee and barrel axes.
- `solve.py` (no browser, about 1 s): reads `L` and `TRAIN` from `movement.js`, solves the escape arbor (9.40 mm from the balance, the fourth's mesh distance from the fourth) against `L.E`, gives each stage's module and wheel tips, and checks in plan that no arbor running through the wheels' levels is inside a wheel's tips; exit code 1 on a disagreement. Re-run it after changing a tooth count or a place in `L`.
- `dyn.py` + `interference-check.js`: 0.4 mm voxel collision check across a full escapement cycle; only intended joints (the `IGN` set) may overlap.
- `fine.py` + `fine-interference.js`: the same idea at 0.05 mm, over the escapement phases, 15 train positions (whole teeth apart) and wind states including full wind and winding, then a real wind through the page's own loop (Wind from 20 minutes short of run down, checked as the key goes on, half wound, as it is let go and a second later; not with `--hold`); it also tests the chain's links and the tube springs. Pairs in its `EXPECTED` table are intended contacts, each with its reason and a size limit; anything new or grown fails (exit code 1). Run it after any geometry change: dyn.py missed four overlaps of 0.1–0.4 mm that this one found (RESOLVED.md, going train and winding). Expected entries include the barrel cap's screws in the lip inside its rim, the chain links on the fusee cone and the chain's end fittings. `--hold` runs it with the balance locking arm locked and the train-blocking screw down; `--dense` adds 101 balance phases; `--split` shows the split-balance variant and fails on open finding 9. It tests the barrel's wall (`userData.barrelWall`) as the solid it encloses, and `barrel-clearance.js` measures (to about 0.002 mm) how close every other part comes to the solid the whole barrel sweeps (wall, caps, cap screws, hook), and where the mainspring lies inside; the tightest is the barrel bridge, 0.55 mm above the boss. `--eval JS` runs code after loading: a variant, `__mv.userData.R.timing(3,3)`, or a planted fault to prove a check. The dial's printed face, an open ring 0.02 mm over its brass disc, is checked exactly instead: no part over the dial, outside its arbor holes, may come within 0.02 mm of it.
- `solids.py` + `solids-check.js`: every mesh closed (no open edge), consistently wound and with a positive volume, as loaded and with Moving parts only and a section on (the mainspring and hairspring are built only when shown); exit code 1 on a failure. Run it after any geometry change.
- `placements.py`: `dump NAME [--page PATH]` records every mesh's position and bounding box in seven model states (escapement phases, train and wind positions, set as `fine.py` sets them); `--diff A B` lists the parts that moved, resized or changed mesh count (matched by box when the count changed). `--page` points at another copy of `index.html` (a worktree of `main`) for a before/after across branches.
- `exploded.py` + `exploded-check.js`: the Exploded view's clearance. Each part, screw and loose piece (`mv.userData.lifted`) is rastered as assembled into vertical columns, giving for every pair the relative offsets at which they meet; none may meet at full spread or pass through each other on the slider's way there. Run it after changing a part's explode offset (`part(name, off)`) or its shape: where parts overlap seen along the arbors, the upper one must rise more. Screws put in through another part use `headOn`, pieces that come off another way `loose`.
- `maintaining.py`: drives the movement through run and wind cycles and checks the maintaining work: the sustaining ratchet never turns back (except its fall to the pawl as winding starts), the sustaining spring is loaded in running and only relaxes while winding, the fusee catches forward when the key lets go, the pawls sit on their teeth, and the stop-bar meets the winding stop at full wind and, swept from full wind to run down, passes it more than the fusee's widest endshake clear. Run it after touching the fusee, the maintaining work or `update()`.

Before merging a branch into `main`, run `python ci.py` on it (with `--full` after a geometry change, `--views` when anything drawn changed) and merge only when it passes; say what it printed. `.gitattributes` keeps text files LF so the built copies compare byte for byte.
- `social.py`: renders the 1200×630 link previews `site-assets/social.png` (dial) and `social-movement.png` (moving parts).
- `p3fit.py`: renders from the top-view photo camera into `r_p3.png`; the committed reference result is `verification/topview-comparison.png`.
- `bom.py` + `bom-check.js` (+ `bom_md.py`): every part against the manual's parts list, `bom.json` (Sec. XI, Figs. 106-110, transcribed line by line, totals checked against Sec. XII; one line per catalogue line, its id the Hamilton number with a suffix where the number is on several lines). Every piece of the model carries its line as `userData.hn` (`hn()` in `core.js`; one object per piece, `{sub:1}` on its other meshes); the check counts them against the units per assembly and measures on the built meshes each line's relations: `in` (a thread, pivot, pin or setting inside the named part: tap, clear, run, free, press, or embed where a hole across an extrusion or turned part can't be cut), `round` (a bore round a shaft, post, pipe or screw), `on` (resting on it), `mesh` (centre distance m(z1+z2)/2, modules, face overlap, ratio through `update()`), `endshake` (0.001-0.003 in, Ops. 15, 69, 74), and the 14 jewels seated. A line's `dev` records a known deviation with its reason (printed `~~`, not failed). Exit code 1 on a failure; `--md` rewrites `BOM.md` at the root; about 5 minutes. **New parts get an `hn()` tag and a `bom.json` line or relation; run it after any geometry change.** `userData.axis` marks the mesh a part turns about where its group's origin is off it.
- `video.py` (no browser; opencv-python, and yt-dlp for `fetch`): teeth and parts from videos of real Model 21s, listed in `References/README.md` ("Videos consulted"). `fetch ID` downloads one into `$MC_VIDEO` (default `~/mc-video`, outside the repository: the videos and their frames are cited, never committed), `sheet ID` makes timestamped contact sheets to find a moment, `frame ID mm:ss` takes full frames, and `count FRAME cx cy a b NAME` counts a wheel's teeth one by one: the rim unrolled along a fitted ellipse, every gap found, the pitch fitted round the turn; `g_NAME.png` marks the gaps and `e_NAME.png` gives eight enlarged segments to count by eye. A wheel seen whole counts exactly; a partly hidden one reads a tooth or two out, so check by eye and against the train's ratios. Its docstring has the commands behind IDEAS.md 1.8's counts. `sheet --from mm:ss --to mm:ss` covers a stretch only; `fit SPEC.json` fits a frame's camera to named model points and circles traced on it, and `unproj` puts pixels back on a plane through it (it needs four or more named points spread over the frame: VIDEOS.md, "Methods"). Heights read along a pillar in a side view (16.8 mm plate to train bridge) are the most reliable measurement.
- `acoustic.py ID [...] [--fetch] [--write]` (no browser; numpy, scipy, matplotlib, imageio-ffmpeg, yt-dlp for `--fetch`): the escapement heard. The clicks inside each beat of recordings of real, running Model 21s (in `$MC_VIDEO`, so `ci.py` can't run it): beats aligned by cross-correlation, bad ones rejected, a trimmed mean in dB over each beat's quiet floor, onsets by the rise of the log envelope with their spread over bootstrap resamples; then `dynamics.js`'s escapement in time (which traces the return swing's trip-spring events and takes `bE`, out of beat) and the old kinematic model (39d6919) fitted with the swing as the free parameter, then with the beat error too, every pairing of events with onsets tried. Prints each fit with its residuals and runner-up, and single intervals read as a swing (strike to lock; the return swing's clicks to the next unlocking, the lift-angle method); `--write` writes `tools/acoustic.json`, plots go to `$MC_VIDEO/acoustic`. Its docstring has the method and thresholds; `References/VIDEOS.md` ("The clicks of a beat") the results.
- `swing.py ID` (no browser; opencv-python, scipy, matplotlib): the balance's swing read frame by frame off a video of a running Model 21 (in `$MC_VIDEO`, so `ci.py` can't run it): the screws' sweep through the plate's cutouts fitted as an ellipse, turning points by mirror symmetry, each turn registered on the same side's two periods on; the start and the growth are known modulo one screw hole (15°), so it gives the aliases and says which is likeliest. `swing.py survey` writes the videos looked at and why each was rejected. Writes `tools/swing.json`, plots to `$MC_VIDEO/swing`. On `We1dLNXiBj0` it measures a start (the balance let go by hand at 0:55), not a steady swing.
- `startup.js` (Node.js, no browser; reads `swing.json` and `acoustic_stretches.json`, so it runs without the video): the video's start run in `dynamics.js`, the drive and the balance's free run-down `TF` fitted to how fast the swing builds up, for each of the video's readings; and the sound's swings against the same fit. It reports, never fails. Model README, "Checked against real chronometers".
- `verification/real-chronometers/` (model folder): the report on the checks against real chronometers (`index.html`, open the file): `build_report.py` writes it from `template.html`, the tools' `acoustic.json`, `acoustic_stretches.json` and `swing.json` and `assets/data.json` (`node reportdata.js`: the model's intervals and the start in `dynamics.js`). The repository's copy links to the videos at the moments used; `--local DIR` builds a fuller copy outside the repository with audio excerpts and the frames (other people's work, never committed). Rebuild it after re-running `acoustic.py`, `swing.py` or changing the escapement.
- `holes.py PART [--bottom] [--plan OUT.png]`: the holes through a part's face read off the built model (centre and radius, movement frame), as JSON for `video.py anchor`; `--plan` draws the face with the holes numbered. `video.py anchor SPEC.json` maps a frame onto that face by a homography fitted on traced circles (the train bridge's rim and its cut round the barrel) and named holes, every other hole a check; specs for the frames used are in `tools/anchors/` (the frames themselves stay in `$MC_VIDEO`).
- `rimfit.py` (no browser; opencv-python, scipy): a plate or bridge lying on the blue mat in a video frame, put in millimetres through a perspective camera fitted to its round rim of known radius, with round settings traced on it made to come out circular (a rim's arc alone leaves the tilt loose); picked points go back onto the plane at their heights above the face and named arbors turn them onto the model's plan, over several focal lengths. `rimfit_36-01.json`: the balance lower bridge on the upturned train bridge (`References/VIDEOS.md`, Methods), which `lower_bridge.py`'s `VIDEO` outline comes from. `rimfit_40-08.json`: the pillar plate's dial side in its mounting ring (`"segment": "silver"`, the rim tied to the centre arbor), the fusee's and indicator's angles about the centre.
- `fcal.py SPEC.json` (no browser): the focal length a frame allows. It runs `rimfit.py`'s model of the frame at a series of focal lengths and prints each fit's cost, rim rms, centre miss and tilt; with a `cut` in the spec it also fits that traced cut's circle, centre and radius free. The video's camera changes focal length between shots (`References/VIDEOS.md`, "The camera's focal length"), so a measurement assumed at f 6000 holds only where this profile has a clear minimum near it; otherwise give the result over the range the profile allows, and check it with a ratio that needs no camera.
- `framecam.py` (`SPEC.json [look | warp RENDER OUT yaw pitch dist] [--f 6000]`): a video frame's camera recovered from the homography `video.py anchor` fitted on it (run that first: it writes the anchor's `.H.json`), the focal length where the face's two axes come out orthonormal. Picks go back on planes at their heights off the anchored face (a part standing 8 mm proud lands several percent off where the face's homography alone puts it); `look` prints the `--look` that has `isolate.py` see the model from that camera, `warp` maps such a render onto the frame beside it. `anchors/lower_bridge_13-49.5.json`: the balance lower bridge on the train bridge's underside, `lower_bridge.py`'s `MEAS`.
- `book.py [--pdf OUT]`: the build book (Making it, Build book) checked as paper: laid out as print at A4's column, each drawing at the scale its title states (20:1 to 1:4, the largest that fits), no taller than a page, its text at least 1.5 mm and its lines 0.1 mm on paper; each sheet's lines with a material and a fit (measured, the other side's, or "not measured" with its function), its size and source; every parts-list line on a part of the model on some sheet (a part with pieces is an assembly page, its lines on its pieces' sheets). `ci.py` runs it.
- `planets_fit.py [--py DIR] [--eph DIR] [--write]` (no browser; skyfield and de440s.bsp as `almanac_ref.py` takes them): Jupiter's and Saturn's heliocentric places as series fitted to DE440 over 1850-2150, tested between the fit's dates and beyond them; `--write` puts them between `shared/almanac.js`'s PLANET-FIT markers. `almanac_ref.py --planets` adds Jupiter and Saturn from Horizons to `almanac-ref.json`, which `almanac.js` checks them against.
- `jewelhole.py FRAME CX CY H0 H1 S0 S1` (no browser): a jewel's hole against its stone on a frame of the setting held to the light: the lit disc's and the stone's edges along 90 rays, circles fitted, their ratio (no camera needed). The escape, third and fourth jewels' holes came from it (`References/VIDEOS.md`).
- `ratchetface.py FRAME --box x0 y0 x1 y1 --c cx cy [--fold OUT.png]` (no browser): a dark ratchet's teeth off its outline on a frame (the setup ratchet held loose, KLUwI2UUCMQ 38:25.8, 38:26.0): the tips' ellipse mapped to a circle, each gap's depth and each locking face's lean against the radius, then the same read off synthetic frames through that ellipse with known teeth, blurred until their edges match the frame's, which turns the readings (blur makes a gap shallower and its face lean back) into true depth and lean. The setup ratchet's 0.48 mm and undercut faces came from it (`References/VIDEOS.md`, Methods).
- `audit.py` + `geometry-audit.js` (`audit.py box` runs `geometry-audit-box.js` for the box and gimbals): flags overlapping screws, screws with nothing under their seat, arbor/pin ends that sit in nothing, coplanar overlapping faces, and parts touching nothing, among the parts shown (`--eval JS` runs code after loading: `--eval "__mv.userData.stop('navy')"` audits the Navy's Y-arm). Screws are found through `userData.screw` (set by `screw()` in `movement.js`). Expected leftovers: the winding-stop pin, the free ends of the balance screws and timing weights' screws, the balance lower bridge's two steady pins and the detent support block's two positioning pins (their holes in the train bridge are drawn through), and the detent's steady pins standing out of its foot, each in its `LOOSE` table with its reason; most coplanar hits are faces in contact, counted per pair of parts and face level in `tools/audit-expected.json`. It freezes the model in `placements.py`'s first state, so a run doesn't depend on the clock, and fails (exit code 1) on any finding not expected; after an intended change of coplanar faces, check what's new, then `audit.py --update` (and `audit.py box --update`). `ci.py` runs both.

The README's "Estimated, not from the manual" section lists which dimensions/tooth counts are guesses versus sourced from the manual; keep that distinction accurate when changing the model.
